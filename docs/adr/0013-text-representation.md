# ADR 0013: 公共 API 文本表示——NUL 字符串、长度视图与混合边界

- 状态：提案（候选方案待评审，本文给出建议但不构成最终决定）
- 日期：2026-09-26

## 背景

cAgentV1 的全部公共文本使用 `const char*`（NUL 结尾）：request 输入、Tool
name/schema、Session 与 Event 字段都是 C 字符串；每次运行在 request arena 中构造
`context`、`tools_json`、`messages_json` 三个 NUL 缓冲交给 Model。该做法与 C 生态
互操作最顺，但依赖隐式长度（`strlen`）、存在截断歧义，且工具输出经共享固定缓冲一次
性交付。

V2 公共头草案改为全线 `agent_string_view_t`（`{const char* data; size_t size;}`，
借用、定长、不保证 NUL），并把三条流式回调（Tool 输出 `agent_text_sink_t`、Model
响应 `agent_model_sink_t`、HTTP body `agent_http_sink_t`）的块单位统一为该视图。
ADR 0009 已将其定为"全部无分配文本输入/输出的统一表示"。

本文记录文本表示的候选方案、取舍依据与建议，供评审最终裁定。该选择影响：全部公共
结构体字段与回调签名、sink 接口形态、与 cJSON（ADR 0006）及 libc 的边界转换、
以及作为开源库的上手成本。

## 评估维度

| 维度 | 含义 |
|------|------|
| 流式与内存上界 | 是否支持分块交付，使内存开销与响应总量解耦 |
| 外来数据安全 | 对模型输出、Tool arguments 中 0 字节的截断免疫 |
| 调用点成本 | 应用侧书写与打印摩擦（DX） |
| 边界转换 | 与 cJSON/libc 之间转换点的数量、位置与有界性 |
| API 面与测试 | 公共符号数量、变体组合带来的测试矩阵 |
| 借用期表述 | 所有权/有效期契约能否被一致地文档化 |
| 决策一致性 | 与 ADR 0001（C99）、0006（cJSON）、0009、0011 及"无 `_simple` 变体"原则的关系 |

## 候选方案

### 方案 A：全线 NUL 字符串（回归 V1 形态）

所有公共文本参数与结构体成员为 `const char*`，调用者保证 NUL 结尾与生存期；工具
输出、模型响应以"调用者/库提供的整段缓冲"交付。

优点：

- 调用点最熟悉：字面量直传、`printf("%s")` 直打，无新概念；
- 与 libc、cJSON、文件/路径等 C 生态零转换；
- 单指针成员在 32 位目标上略省空间。

缺点：

- **三条 sink 无法流式**：NUL 块必须自带结尾，生产者从接收缓冲切出的片段需逐块
  拷贝并补 `'\0'`；块内出现 0 字节即静默截断；空块语义不明。Model/Tool/HTTP 的
  分块交付需退化为"先完整攒一份"，内存上界与响应总量耦合；
- 投影链逐层拷贝或 `strlen`，V1 的重复计算与峰值耦合问题回归；
- 有界缓冲的"截断 vs 自然结束"歧义需要额外 out-length 约定逐接口弥补；
- 外来数据存在 NUL 截断面，与"一切有界、显式长度"的内核原则冲突。

### 方案 B：全线长度视图（当前草案形态）

公共 API 一律 `agent_string_view_t`；字面量经 `AGENT_SV_LITERAL`，运行期字符串经
`agent_string_view(data, size)`；打印用 `%.*s`。

优点：

- 三条 sink 原生流式：`(指针, 长度)` 块零拷贝、二进制安全、空块可表达，内存上界
  只与块大小相关；
- 长度随数据穿越所有层，截断显式化（`agent_response_t.output_written/required`）；
- 投影链零拷贝借用，模块间无重复 `strlen`；
- 单一表示，无第二套规则需要学习。

缺点：

- 调用点摩擦真实存在：应用持有的 NUL 串必须手写长度（当前头文件缺少
  `from_cstr` 便利函数，是最明显的 DX 缺口）；
- 打印、日志、调试姿势与习惯不同（`%.*s`）；
- 借用期契约依赖文档与示例守护，C 编译器不提供保护。

### 方案 C：视图内核 + 应用边界便利层（建议方案）

内核与模块间接口维持方案 B 不变；在**应用边界**补充便利设施，把摩擦从"每个调用
点"压缩到"文档一页 + 少数辅助函数"：

1. `types.h` 增加
   `static inline agent_string_view_t agent_string_view_from_cstr(const char* s)`
   （内部一次 `strlen`；`s == NULL` 返回空视图）。架构 §18.3 已预留该路线：
   "长期静态字符串可以继续提供以 NULL 结尾的便利入口，但内部转换为带长度视图"；
2. 保留并推广 `AGENT_SV_LITERAL` 作为字面量标准姿势；
3. 注册/请求入口**维持单一视图签名**，不提供成对 cstr 变体（一致性理由见方案 D）；
4. README/文档增设借用语义专页（BORROWED/VIEW、各接口借用期表）与三种调用姿势
   的对照示例。

优点：

- 完整保留方案 B 的结构收益（流式、零拷贝、定长、0 字节免疫）；
- 应用侧常见场景降为 `from_cstr(app_buf)` 一词开销；
- 转换成本集中在明确声明的边界，内核不引入 NUL 假设。

缺点：

- 仍非纯 NUL 体验；`from_cstr` 本身是一次 O(n) 扫描（仅发生在应用边界，可接受）；
- 便利层的文档与示例是必交付项，欠账则 DX 收益无法兑现。

### 方案 D：双轨公共 API（view/cstr 成对变体）

每个文本入口同时提供两个变体，如 `agent_register_tool()` /
`agent_register_tool_cstr()`。

优点：两类调用者各自零摩擦。

缺点：

- 公共 API 面约翻倍，测试矩阵同步翻倍；
- 与架构 §18.2/§26.11"不提供 `_simple` 便捷变体、单一完整结构体注入"原则直接
  冲突，且开了先例（下一个问题就是 `_cstr` 的注册、请求、sink 要不要全套）；
- cstr 变体内部仍需转换为视图，转换成本未消失，只是搬进库内并翻倍出现。

### 方案 E：C11 `_Generic` 自动分派

提供 `agent_str(x)` 类宏，按实参类型在 `char*` 与视图之间自动分派。

被既有决策约束：项目语言基线为 C99（ADR 0001），`_Generic` 为 C11 特性，且部分
目标工具链（armcc 等）C11 支持参差。**本方案暂不启用**；若未来语言基线升级 C11，
可作为方案 C 之上的体验增强重开评审。

## 方案对比

| 维度 | A 全 NUL | B 全视图 | C 视图+边界便利 | D 双轨 | E `_Generic` |
|------|----------|----------|----------------|--------|--------------|
| 流式/内存上界 | 不支持 | 支持 | 支持 | 支持 | 支持 |
| 外来 0 字节安全 | 截断面 | 免疫 | 免疫 | 免疫 | 免疫 |
| 调用点 DX | 最熟 | 摩擦最高 | 摩擦低 | 两类均零 | 零（若可用） |
| 边界转换 | 零（全 NUL 世界） | 集中于 codec 边界 | 集中于 codec 边界 | 库内翻倍 | 同 C |
| API 面/测试 | 最小 | 最小 | 最小+1 函数 | 约翻倍 | 同 C |
| 决策一致性 | 违背有界原则 | 一致 | 一致（兑现 §18.3） | 违背无变体原则 | 违背 C99 基线 |

## 建议决定（待评审确认）

采用**方案 C**：

1. 内核、模块间与全部回调保持 `agent_string_view_t` 单一表示；三条 sink 的块单位
   维持视图；
2. `types.h` 新增 `agent_string_view_from_cstr()`，`AGENT_SV_LITERAL` 保留为字面量
   标准姿势；
3. 公共入口不提供成对 cstr 变体；若评审确认高频痛点，仅允许在注册入口按
   评审重点 1 复议；
4. 视图 ↔ NUL 的转换只允许出现在 codec/provider/storage 边界（有界拷贝 + 终止符
   写入 run scratch 或 provider 自有缓冲），内核代码不得出现 `strlen/strcpy` 类
   NUL 假设；
5. 借用语义专页与调用姿势示例列为头文件定稿的前置交付项。

## 不采用的方案

- **方案 A（全线 NUL）**：放弃流式与显式长度，等于撤回 V2 内存模型的两条支柱；
  拒绝。
- **方案 D（双轨 API）**：API 面与测试矩阵翻倍，违反无变体原则，转换成本未消除；
  拒绝。
- **方案 E（`_Generic`）**：受 C99 基线约束，暂不启用；语言基线变更时重开。

## 影响

正面影响：

- 三条 sink 保持分块流式，Model 响应、Tool 输出、HTTP body 的内存上界与总量解耦；
- 外来文本的 0 字节截断风险在类型层面消除；
- 应用侧常见调用降为单一便利函数，DX 缺口闭合；
- 内核零 NUL 假设，`strlen/strcpy` 类隐患可用静态审计约束。

代价：

- 应用侧仍需学习视图与借用语义（靠文档与示例偿还）；
- `from_cstr` 为应用边界一次性 O(n) 扫描；
- codec/provider 边界的转换代码为长期固定成本。

## 评审重点

1. 方案 C 第 3 条（不提供 cstr 注册变体）是否接受；若产品侧反馈强烈，候选折中是
   仅对 `agent_tool_t`/`agent_skill_t` 的 `name/description/schema` 提供
   cstr 便捷入口，还是维持单一签名。
2. `AGENT_SV_LITERAL` 的命名与形态是否顺手（备选：缩短为 `AGENT_SV(...)`）。
3. `name`、`description` 等"几乎总是字符串字面量"的字段是否值得在文档中单独给出
   推荐姿势，而非引入新机制。
4. `agent_string_view_from_cstr()` 的契约：`NULL → 空视图`、长度即 `strlen`、
   调用者保证生存期——是否需要同时约定"不得指向内核借出缓冲"。
5. 打印/日志姿势是否需要库内提供辅助宏（如 `AGENT_SV_FMT`/`AGENT_SV_ARG`），
   或仅由文档统一示例。
6. 是否先落地最小 example（字面量 / `from_cstr` / `%.*s` 三姿势）实测 DX，
   再定稿本 ADR。

## 验证要求

- 每个公共头可独立以 C99 与 C++11 编译；
- `agent_string_view_from_cstr()`：`NULL` 返回空视图、普通串长度正确、超长串
  行为符合契约文档；
- 三条 sink 的流式测试覆盖：含 0 字节的块、空块、多块顺序与总长度校验；
- 内核代码审计：`src/core`、`src/run`、`src/session` 等内核目录不得出现
  `strlen/strcpy/strcat` 等 NUL 假设调用（codec/provider 目录除外，且必须使用
  有界目标缓冲）；
- example 覆盖三种调用姿势，并进入公共头独立编译测试矩阵。
