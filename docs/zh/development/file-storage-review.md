## 读取一致性与文本边界

`agent_file_read_all()` 的流程是 size、精确读取、EOF 探测、再次检查 size。
该流程不创建原子快照，也不能保证发现所有并发修改。同长度覆盖或替换可能通过
检查；分块读取期间也可能混合不同版本。后端按名称多次打开文件时，仅限制一个
Store 实例串行调用不足以排除其他实例或外部进程修改同一文件。

调用方必须协调所有相关写入方，保证整个读取期间文件稳定。本次已采用以下注释：

```c
/* Bounded whole-file read, not a snapshot; caller excludes concurrent writes/replaces. */
```

不建议改名为 `read_all_serialized`，它容易让人误以为函数内部负责加锁。
新增同长度变化的边界测试明确展示的是检测能力的限制，不是支持并发修改
的承诺。不能把“应该检测所有竞争”作为当前接口的验收目标。

未来 User/Memory 的链路应分别落实两个责任：

```text
应用协调读写，保证文件稳定
  -> 有界读取到应用持有的缓冲
  -> 领域组件验证并选择内容
  -> 在 turn 边界切换到新版本
  -> 当前请求期间保持该缓冲和内容不变
```

前半段保证读取一致性，后半段保证 Context 借用内容的生命周期。文件辅助不负责
更新调度、缓存失效、Memory 检索或写入授权。

`read_text` 拒绝内嵌 NUL，并追加字符串终止符；这是文本辅助的接口约定，不是
完整 Markdown 或 UTF-8 校验。Session JSONL 通过字节读取后再进行格式解析；
二进制附件应使用 `read_all/read_exact`，不放宽文本辅助的约束。

## 删除、发布与同步失败

`clear_all` 只清理符合 Session 文件名规则的文件，不提供跨文件事务。中途出错时，
前面已经删除的文件不会恢复；调用方不能依据返回错误推断数据完全未变化。

单文件删除也可能出现“文件已删除，但目录同步失败”。重新调用可能得到
NOT_FOUND，不能把该结果直接解释为第一次没有执行删除。

整文件替换已经提供 `published`，应保留它区分两个阶段：

| 结果 | 含义 |
|---|---|
| 错误，published=false | 本次新版本未发布；不代表其他写入方没有修改文件 |
| 错误，published=true | 本次新版本已经发布，后续同步失败；不能当作未写入盲目重试 |
| 成功，published=true | 新版本发布且所请求的同步调用成功；不等于完成掉电验收 |

Turn 提交存在同构的两阶段歧义：`jsonl_finish` 先追加完整行，再请求同步；同步
失败时，完整记录可能仍然可被读取，甚至已经具有耐久性，但错误返回无法确认这些
结果。Provider 已结束事务，Core Session 也会关闭本轮，不能对同一事务重复调用
`finish()`。依据见 [JSONL 提交实现](../../../providers/storage/jsonl/src/session_jsonl.c)
和 [Core Session 实现](../../../src/session/session_manager.c)。

尾部修复只截掉没有结束换行的残尾，不撤销完整行、不判断重复 turn，也不恢复
本轮提交的确定结果。不能将它描述为“下次 begin 会自愈提交歧义”。现有记录没有
稳定的唯一 turn_id，按文本相同或仅检查尾部内容不能获得可靠的幂等判定。

FS-11 的 MVP 建议如下，仍需在接入 `agent_run()` 前裁决和实现，不是已完成行为：

- 提交失败后不自动重提该 turn，也不自动重跑整个模型与 Tool 链路；后者可能
  重复控制设备或产生其他外部副作用。
- 向应用报告存储提交失败，不声称日志未改变，也不把耐久性未知解释为已经保存。
- 后续历史允许包含该完整记录；这一点必须纳入运行返回值与事件语义的说明。
- 补“完整追加成功、同步失败、事务关闭、后续回放仍可见”的 Host 用例，并验证
  下一次 begin 不会删除该完整行。该用例验证可见性，不验证掉电耐久性。

需要稳定 turn_id、幂等写入或可查询提交结果时，应另行设计领域提交协议，不能
将其当成文件层尾部修复的一部分。当前不扩大公共 API。

删除契约与故障测试已经补充；仍不为删除扩展结果结构，也不实现批量删除回滚。
只有真实消费者需要更强保证时，再评估额外结果或事务机制。

## JSONL 版本与容量约束

FS-12 包含两个独立事实：`digit()` 要求数值原文为单个十进制数字；版本校验仅
接受 1。`v:2` 符合前者，是被后者拒绝；`v:10` 则会在数值格式检查时失败。
角色和 outcome 还要分别通过各自合法值检查，单数字解析成功不等于字段合法。
当前未知版本与畸形记录均返回 `AGENT_ERROR_PARSE`，不静默跳过。这是当前错误
分类取舍，不表示兼容未来版本。见
[JSONL 记录解码](../../../providers/storage/jsonl/src/jsonl_record.c)。

FS-13 中的容量都按一份 turn 记录计算，不是整个 Session 历史的总容量：

| 配置 | 当前作用 |
|---|---|
| read_message_capacity | 解码消息槽位数，同时限制编码时的消息总数 |
| read_call_capacity | 解码 Tool call 槽位数，同时限制编码时所有消息的调用总数 |
| write_line_capacity | 编码 JSONL 行的字节缓冲，包含 JSON 转义及结尾开销 |
| read_line_capacity | 回读单行缓冲，需要容纳读取的内容和字符串终止符 |
| token_buffer_bytes | 回读 JSON token 容量；字段与数组规模也可能导致容量不足 |
| decoded_capacity | 解码字符串缓冲容量，并非原始 JSON 行长度 |

共用数量上限有助于保持读写规模一致，但不保证完整回读：write_line 足够大而
read_line、token 或 decoded 容量不足时，写入仍可能成功，recent 却返回 CAPACITY。
若产品要求该实例能回放自身写入的记录，应用必须配置匹配预算，并用最大允许
记录验证；不能仅比较两个行缓冲大小就宣称保证。字段注释与相关测试仍待补充，
本次只修正文档，不改变配置或实现。

## 能力、安全与平台验证边界

- ops 回调存在表示提供了对应操作；缺失表示不支持。绑定期属于运行期，提前拒绝
  缺失能力不等于在编译期验证文件系统，也不保证所有后续调用都会成功。
- `sync_directory` 是同步请求配置。初始化尝试目录 fsync 可提前发现部分不支持
  情况，但不能证明媒体掉电耐久性、所有目标文件系统的 rename 语义或未来调用成功。
- 当前 `lstat` 与可用时的 `O_NOFOLLOW` 用于叶子文件检查，不构成抵御恶意并发
  目录替换的完整沙箱；可信稳定目录是部署前提。
- `AGENT_POSIX_FILE_STORE_NO_SYMLINKS` 是无符号链接挂载的显式构建配置，不是
  自动检测能力；不能将它作为存在符号链接时的安全退化方案。
- `.cagent-*` 私有前缀用于隐藏临时文件并避免普通消费者访问。Session 自身还会
  校验 `session-<hex>.jsonl`，临时文件原本就不符合其清理规则。
- ESP-IDF/OpenVela 的薄入口复用兼容 POSIX 实现，不表示所有 VFS 挂载已验证。
  Host 契约测试及目标编译检查不能替代真实挂载、重启和掉电测试。
