# ADR 0030: 可选共享文件 I/O 的边界

- 状态：提案（不变更现有公共接口，暂不实施迁移）
- 日期：2026-10-02
- 关联：[ADR 0023](0023-file-backed-memory-soul-skill.md)、[ADR 0026](0026-session-file-io-adapters.md)、[ADR 0027](0027-minimal-markdown-memory-layout.md)、[ADR 0029](0029-official-skill-file-loader.md)

后续方案见 [ADR 0031: 预制平台文件存储与读取](0031-prefabricated-platform-file-storage.md)。
本文保留共享 I/O 的早期评估；ADR 0031 以 JSONL Session 与 `USER.md` 有界读取
验证统一文件契约，并调整下文关于安全相对打开、目录同步和迁移触发的建议。
两份文档均未冻结新的 C API。

## 背景与现状

JSONL Session Provider 通过 `agent_session_jsonl_file_ops_t` 接受应用提供的
`size/read/append/truncate/sync/remove/clear_all/count`，不直接依赖文件系统。
可选 POSIX 适配器实现这八项操作：将任意 Session ID 十六进制编码为
`session-<hex>.jsonl`；`count` 与 `clear_all` 只对该前缀后缀同时匹配的文件名
生效，不触碰目录中其他条目。该适配器要求目标文件系统提供
`open/read/write/lseek/ftruncate/fsync/stat/opendir/readdir/unlink`，并在
`fsync` 不可用时返回错误而不是假装成功。

这些接口解耦了 JSONL 格式与平台 API，但并非全库通用文件契约：按 Session
ID 寻址、文件名映射以及 `clear_all/count` 的作用范围都具有 Session 命名空间
语义。简单移动头文件或重命名类型，不能让它安全地服务 `USER.md`、
`MEMORY.md`、每日笔记和 Skill 目录。

**共享已经发生，只是发生在平台维度上。**ESP-IDF 与 OpenVela 两个装配层都
直接绑定 `agent_posix_session_file_ops()`，与 Host 共用同一份实现；两者的
README 也已各自声明 `fsync` 成功不等于掉电持久。因此本文要裁决的不是
"要不要抽象"，而是：

> **要不要允许第二个领域（Skill 加载器、Memory 读取）依赖这个已经存在、
> 且已被三个平台共用的 Session 形状接口？**

这一区分决定了下节候选方案的读法：第一行"各领域独立实现"不是维持现状，
而是让新领域绕开一个已在运行的共享层另起一套。不把不同领域的加载、注册、
检索或提交语义合并为一个 Storage Provider。

## 候选方案

| 方案 | 收益 | 代价或风险 |
|---|---|---|
| 各领域独立实现文件访问 | 现有 Session 无迁移成本 | 绕开已运行的共享层，平台细节、安全检查与测试重复 |
| 直接将 Session file ops 提升为通用接口 | 表面改动少 | Session ID、批量清理和精确读取语义泄漏到其他领域 |
| 在可选层抽取共享物理 I/O，保留领域适配 | 复用文件机制，保留不同领域契约 | 需要真实第二消费者和跨目标验证来收敛接口 |

倾向第三种方案，但**当前只记录边界，不迁移代码或冻结新的 C API**。

## 第一个消费者的耐久性义务

共享物理层无论何时抽取，都是从一个已经在跑的适配器里提炼出来的。因此必须在
抽取前清偿第一消费者的欠账，否则共享层继承的是缺口而不是能力。

现状：JSONL Provider 每次追加后确实调用 `sync`，追加与同步的调用关系是完整的；
但 POSIX 适配器的 `sync` 是对已打开文件描述符的 `fsync`，**父目录从未同步**。
对 `O_CREAT` 新建的文件，目录项可能尚未落盘，而该次 `sync` 返回 `AGENT_OK`。
文件内容同步、目录项同步与文件系统及介质行为是三个独立事实，任一成立不蕴含
其余成立。

据此确定前置义务：

- Session 文件适配器在完成一次 turn 提交后，除文件同步外还须提供目录项同步，
  或在其支持声明中显式排除新建文件场景，不得静默降级。
- "摘要 + 同步"这类复合原语若将来进入共享层，其语义须明确定义为
  "内容与目录项均已请求同步"，且失败不被吞掉；无法兑现的目标文件系统应被
  明确拒绝该能力，而不是返回成功。
- 该义务属于 Session 消费者自身的待验证项，**不因共享层推迟而顺延**；本文
  只记录它，不在此处展开实现细节。

## 提议边界

```text
Application: 选择根目录、挂载、命名空间、容量与授权
  -> 可选平台文件 I/O: 有界字节访问、寻址与目标文件系统适配
      -> Session 文件适配: ID 编码、session-*.jsonl 过滤与批量操作
          -> JSONL Provider: 完整 turn 提交、回放与尾部修复
      -> Skill 加载器: 目录清单、格式解析、显式注册与回滚
      -> Memory 实现: Soul/User 快照、记忆检索与授权更新
Core: 只接受领域数据的有界投影，不打开文件
```

- 共享层只负责文件访问，不解释 JSONL、Markdown、front-matter、Session
  ID、Skill 注册或 Memory 检索；也不决定哪些文件可被模型写入。
- 文件名和目录由应用授权并限定在各自命名空间。Session 的 `clear_all/count`
  仍只作用于 Session 文件；不能因共享物理层而变成对整个根目录的操作。
  `SOUL.md` 与 Skill 的只读信任边界、按用户隔离的 `USER.md` 和 Memory 文件
  都由对应领域或应用约束。模型输出不得直接成为文件路径或授权依据。
- 对只需读取的消费者，不强制提供写入能力。文件访问层不要求 Core、无文件
  系统目标或仅使用 RAM Session 的产品链接平台文件库。文件缓冲及必要的
  遍历清单由应用或可选组件单独预算，不从 Core workspace 隐式分配。

### 寻址与路径解析（先决决定）

寻址方式是文件抽象里最主导的接口决定：它先于读取、枚举、写入的形态，并直接
决定路径逃逸与符号链接防护能不能成立。候选方案表中没有单列它，是因为它不该
等到"比较两个消费者的需求"时再定——它是三个消费者（Session、Skill、Memory）
共同的前提。

需要把"按 Session ID 寻址 + 文件名映射"拆成两部分，而不是整体判为 Session
专属语义：

| 组成部分 | 归属 |
|---|---|
| `session-<hex>.jsonl` 具体映射、`clear_all/count` 的批量范围 | Session 领域语义，留在其适配层 |
| 不透明 ID → 命名空间内路径的映射、保留前缀做命名空间隔离 | 每个消费者都需要，是共享层的候选内容 |
| 相对目录描述符打开（`openat` 语义） | 见下，安全前提要求 |

现有实现不满足第三项：POSIX 适配器把应用目录串与文件名拼成绝对路径后按路径
打开，每次操作重新拼接、重新打开。这在符号链接替换面前留有窗口——先检查
再按路径打开，两次调用之间目标可被替换。ADR 0029 已对此提出明确要求：
Skill 加载器的 Port "应使用目标支持的安全相对打开方式，不能实现时须限定为
应用控制且导入期间不可变的目录，或拒绝该组合"。该要求同样适用于 Session 与
Memory。

因此：

- 共享层若成立，其寻址接口应以"目录描述符/句柄 + 命名空间内相对名"为准，
  而不是以拼接后的路径字符串为准；是否需要跨调用持有描述符由一致快照与
  并发修改要求决定，本文不提前承诺形状。
- 白名单回调、字符串前缀检查都不构成路径隔离，不得作为符号链接防护的替代。
- 目标文件系统不支持安全相对打开时，该能力应被拒绝并写下部署前提，而不是
  以"仅做前缀检查"的方式提供看似隔离的接口。

### 其余原语候选，不是接口承诺

| 需求 | 现状与候选边界 |
|---|---|
| 有界读取 | 现有 Session `size/read(offset)` 要求精确读取；普通文件读取还需确定文件在两次调用间变化、短读和句柄生命周期的语义。不能直接假定两次按路径打开得到同一快照。 |
| 目录枚举 | Skill 加载器需要有界文件名清单；底层只负责枚举，过滤和稳定排序由加载器在调用方预算的空间中完成。枚举期间的目录变化、名称长度和符号链接策略须明示。 |
| 追加 | Session JSONL 已使用 `append`；每日笔记是否采用追加、如何界定完整记录与去重，属于 Memory 领域决定。 |
| 整文件替换 | `truncate + append` 不提供失败后旧版本完整可读的保证。`MEMORY.md` 或 `USER.md` 有真实写入需求时，再确定临时文件、替换、恢复及旧/新版本可见性的契约。 |

即使后端使用临时文件和 `rename`，也不能仅凭函数调用成功宣称掉电原子或
持久。数据同步、目录同步、文件系统及介质行为必须分别验证；不具备要求的
目标应明确拒绝该能力或采用经过验证的其他保存策略。首版不预设一个跨所有
平台都有效的"原子等级"枚举。

## 迁移触发与顺序

1. 保持现有 `agent_session_jsonl_file_ops_t`、JSONL Provider 和 POSIX Session
   适配器的行为与测试不变。仅有一个领域消费者时，不为目录对称预建通用包。
2. 当官方 Skill 单文件/目录加载器或 Memory 文件读取得到真实产品验证，比较
   其文件访问需求与 Session 适配器，再提炼共享的有界读取、寻址与错误处理。
   是否需要文件句柄由一致快照和并发修改要求决定，不提前承诺接口形状。
3. 若确有第二种写入消费者，再裁决追加与整文件替换的语义、能力可用性和
   掉电恢复；Session 可以复用底层辅助，但 ID 映射和批量操作仍留在其适配层。
4. 迁移须保留现有公开 JSONL 配置的使用方式，或单独提出兼容方案；不能将
   "换一处 include"视为完整迁移。Host 契约测试和目标文件系统验证均通过后，
   才能把新文件包标为相应平台可用。

### 触发条件的证伪判据

上述顺序描述的是"何时开始提炼"，还需同时给出"何时应当放弃"。两条判据，
在第二消费者出现时一并评估：

- **体量判据**：抽掉平台层与领域层后，统计两个消费者真正重复的代码行数。
  若重复仅限于短读短写循环与 `errno` 错误映射（数十行量级），则不构成抽象
  理由，应各自保留适配层。共享层必须换回可测量的收益，而不是"看起来更整洁"。
- **方向判据**：比较两个消费者的寻址与一致性需求是否同向。Session 以追加
  提交为语义，Skill 加载器以增量枚举加逐文件有界读为语义，Memory 若需要
  整文件快照一致，则与追加语义方向相反。两个需求方向相反的消费者之间找不到
  同时满足的共享面，此时共享层只应在"寻址 + 有界读取 + 目录枚举"这一薄层
  浮现，写入侧永久各留各家。

结论：继续观察的不是消费者数量，而是**寻址需求是否同向**。数量满足而方向
相反的场合，应明确否决共享层，而不是无限期挂着。

## 验证要求

- 同目录存在 Session、Skill、Soul 和 Memory 文件时，Session 的统计、删除
  不得触及其他命名空间；旧 JSONL 回放和尾部修复行为不变。
- 有界读取在文件增长、缩短、短读及容量不足时不返回截断的成功结果；枚举
  容量不足时不进行部分注册，文件排序可复现。
- 路径逃逸、符号链接及并发替换风险依目标文件系统能力测试或明确限定部署
  前提；仅对字符串做前缀检查不等同于目录隔离。
- 替换失败、同步失败、重启与掉电分别测试；无法验证的耐久性不写成保证。
  可选适配器的内存、文件描述符和最坏延迟不计入 Core 零 heap 承诺。

## 与其他 ADR 的关系

ADR 0023 的"统一编排而非统一领域 Storage ops"不变。ADR 0026 的可选
Session 文件适配器继续有效，是本文所述共享层的直接先例；本 ADR 只提出
未来可复用的物理层，并追加了该适配器尚未完成的目录同步义务。ADR 0029
的 Skill 加载器触发条件、显式注册和排序责任不因共享 I/O 而改变；其"安全
相对打开"要求已被本文吸收为共享层寻址的先决条件。ADR 0027 的四类
Markdown 布局不是通用文件 API 的强制路径规范。

## 待裁决

1. Session POSIX 适配器的目录同步义务由谁验证、在哪些目标文件系统上验证？
   无法兑现时是降级为"仅内容同步"并在契约中声明，还是拒绝该平台可用性？
2. `agent_session_jsonl_file_ops_t` 的精确读写语义是否需要在共享层之前先行
   收敛为"目录描述符 + 相对名"？若是，属修改已发布接口的窗口期任务，须在
   Skill 加载器落地前完成，还是可以与其并行？
3. 哪些目标文件系统能兑现选定的替换、同步和目录隔离语义？不能兑现时采用
   什么降级或替代后端？
