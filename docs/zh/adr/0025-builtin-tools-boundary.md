# ADR 0025: 内置 Tool 的边界与可选能力

- 状态：提案
- 日期：2026-10-01
- 关联：[ADR 0020](0020-synchronous-run-mvp.md)、[ADR 0023](0023-file-backed-memory-soul-skill.md)、[ADR 0024](0024-session-to-memory-extraction.md)

## 背景

智能家居等产品可能需要让模型读取 Skill、检索或写入 Memory，也可能希望从
Session 生成摘要。问题是这些能力是否都应作为 cAgent 默认内置的 Tool。
Tool 一旦注册并投影给模型，就会占用 registry 槽位、请求中的 schema 容量和
模型上下文预算，还会引入模型自主调用、权限判断与失败处理。不是所有内部
能力都应暴露为模型可调用的操作。

本 ADR 将 **Tool 机制**、**可选通用 Tool** 和 **产品 Tool** 分开裁决。

## 方案比较

| 方案 | 优点 | 主要代价 |
|---|---|---|
| 默认注册一组内置 Tool | 上手快，示例统一 | 强加模型协议、容量与权限语义；没有相关后端时仍需处理占位功能 |
| Core 仅提供 Tool 契约和 registry | 最小依赖，产品完全可控 | 常见能力可能在多个产品中重复实现 |
| Core 不自动注册，另提供可选通用 Tool 包 | 保持最小核心，并可复用已验证能力 | 需要明确后端注入、构建裁剪及兼容性测试 |

选择第三种：**MVP 默认内置零个模型可见 Tool**。Core 负责 Tool 注册、投影、
调用、限制和事件等通用机制；确有多个产品复用且边界稳定的能力，才作为
可选实现交付。应用显式选择、构建并注册，不由 `agent_init()` 自动安装。
设备控制、帐号操作等始终由产品定义，不进入通用内置目录。

## 能力分类

| 能力 | 是否适合作为可选 Tool | 理由与边界 |
|---|---|---|
| `read_skill` | 有条件适合 | 仅按已注册的 Skill 标识读取有界内容；不能接收任意文件路径。若 Skill 全文已投影进 Context，再提供此 Tool 通常重复 |
| `memory_search` / `memory_read` | 有条件适合 | 适合模型主动深入检索；也可由 Context Builder 自动检索，两者应按产品需要选择，避免重复注入 |
| `remember` / `forget` | 有条件适合 | 模型只能提出请求；应用或 Memory 后端负责用户范围、授权、确认、去重、提交与删除，成功回复必须以真实提交为准 |
| `summarize` | 默认不是 Tool | Session 摘要/长期记忆提取是应用调度的后台任务或内部流水线，不应依赖模型自行决定何时压缩历史 |
| 设备查询与控制 | 不进入通用库 | 设备协议、实时状态、权限和副作用属于产品；示例可演示注册方法，但不是默认功能 |

这里的 `read_skill` 与 `summarize` 是候选能力名称，不是本 ADR 新增的公共 API
或已实现功能。产品若确需“请总结这段文本”这样的对话 Tool，可自行注册；
它与 ADR 0024 的 Session 到 Memory 提取不是同一职责。

## 装配与信任边界

- 可选 Tool 使用现有 `agent_tool_t` 契约和普通注册流程，不获得绕过 policy、
  limits 或事件的特权。构建选中源码不等于运行时注册；未注册时不占用 Tool
  槽位或模型请求中的 schema 空间。
- 实现通过应用注入的受限能力读取 Skill/Memory，不直接依赖 POSIX 路径、
  Flash、NVS 或特定文件系统。`read_skill` 只能访问本次调用者可见且已注册的
  Skill；不能把 `soul.md` 当 Skill 读取，也不能因发现 Markdown 文件就激活 Skill。
- `AGENT_TOOL_READ_ONLY`、`AGENT_TOOL_SIDE_EFFECT` 等标志只描述操作性质，不
  建立授权。当前 `agent_tool_context_t` 没有受认证的用户/租户身份，因此
  可选 Memory Tool 必须从应用注入的可信上下文确定作用域，不能相信模型
  arguments 中的用户 ID、路径或权限声明。
- 写入与遗忘属于副作用操作；需要确认时遵守同步 MVP 的失败关闭规则，不能
  因 Tool 标了 `REQUIRES_CONFIRM` 就自动批准。普通 Tool 不得修改 Soul，
  Session 原始历史也不得因摘要或遗忘 Memory 而被隐式删除。
- Tool 输出、参数和 Skill/Memory 文本按不可信内容处理；约束名称、参数、
  输出字节数、截止时间和取消点。返回内容不能泄露后端物理路径或跨用户数据。
- 回调和应用状态遵守借用生命周期。底层 I/O 或模型 Provider 如需 heap，需
  单独声明其内存域；不能把它计为 Core workspace 的零 heap 保证。

## 分阶段落地

1. 先完成并验证 Tool registry、同步执行链和 Skill/Memory 的实际读取与写入
   契约。当前公共头文件中的声明不代表这些链路已可用。
2. 在产品或示例中验证 `read_skill` 与显式 `remember` 的权限、容量和用户体验；
   多个产品确有复用时，再提炼为独立可选实现，不提前扩展 Core 公共 API。
3. Session 摘要按 ADR 0024 实现为独立的有界提取任务；只有明确的产品需求
   才考虑另行暴露对话式 `summarize` Tool。

可选实现的目录、名字与编译选项在接口和测试稳定后决定。不要为目录对称而
预建空包，也不要让 Core 依赖某个具体 Tool 实现。

## 验证要求

- 不编译或不注册可选 Tool 时，Core 与无 Tool 的 Agent 仍可构建和运行，
  不产生默认 schema、槽位占用或额外模型调用。
- 已注册 Skill 与未注册文件、其他用户 Skill、Soul 之间有可测试的隔离；
  超长内容与无效标识给出明确的有界失败。
- Memory 写入失败、确认缺失、取消与超时不能被报告为成功；重复调用和
  遗忘对缓存/索引的影响可测试。
- Tool 调用次数、输出大小、请求 schema 与峰值内存均在产品预算内；设备
  控制 Tool 不会因通用 Tool 包的存在而被自动暴露。

## 待定问题

- Skill 是否需要独立的按标识读取接口，还是仅复用注册时借用的 `content`；
- Memory 检索/提交契约与可信调用者身份如何由应用注入；
- 可选 Tool 的代码位置与构建目标，在首个真实产品和契约测试后确定。
