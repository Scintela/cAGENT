# ADR 0024: 从 Session 派生长期 Memory

- 状态：提案
- 日期：2026-10-01
- 关联：[ADR 0010](0010-context-projection.md)、[ADR 0016](0016-session-history-storage.md)、[ADR 0023](0023-file-backed-memory-soul-skill.md)

## 背景

产品会保留原始 Session 历史，同时希望从多个 turn 中概括经历、提取用户偏好与
长期有用的事实，保存为可检索的 Memory。这里的“压缩”可能指三种不同操作：

1. **Context 裁剪**：本轮只投影部分完整 Session turn，以适应模型输入预算；
2. **历史摘要**：把若干 turn 概括为一条有来源的阶段性记忆；
3. **事实提取与整合**：抽取偏好、纠错或任务经验，并与已有 Memory 去重、更新。

只有后两者会产生或修改长期 Memory。摘要有损，不能替代原始 Session，也不能
作为执行过 Tool 或设备动作的唯一证据。Memory 中保存的是**派生内容**，不是
对 JSONL Session 文件的压缩归档。

## 方案比较

| 方案 | 触发方式 | 优势 | 主要代价或风险 |
|---|---|---|---|
| 应用规则提取 | 产品代码识别明确字段或用户命令 | 可预测、低模型成本，适合设备配置与明确偏好 | 覆盖不了自由表达和跨轮归纳 |
| Agent 调用 Memory Tool | 模型提出记住、修改或遗忘 | 意图可见，可对敏感写入加确认 | 增加 Tool 与授权规则；模型可能误记 |
| 每轮自动提取 | 完整 turn 提交后自动调用提取器 | 可及时发现候选记忆 | 额外延迟、费用、能耗与写放大；不宜强制绑定 `agent_run()` |
| 空闲期/定期批处理 | 应用按容量、水位或产品计划调度 | 可合并多轮事实，减少交互路径延迟 | 要管理进度、重试、去重和电源中断 |
| 用户直接编辑 Memory | 产品 UI 或管理接口修改 Markdown | 来源明确，便于审查与纠错 | 依赖产品交互能力 |

## 决定

采用**应用可选择的混合制**，不在 Core 中强制自动提取，也不把 Memory 写入
限定为 Tool 调用：

- 首阶段允许产品确定性写入，以及显式的记住/遗忘 Tool；Tool 只能提交写入
  **请求**，实际准入、用户范围与落盘由应用或 Memory 实现裁决。
- 自动提取是可选的后台或空闲期工作；产品配置触发水位、提取模型、预算和
  是否需要用户确认。默认不因每个 turn 完成就额外调用模型。
- 无论触发来自规则、Tool、用户还是后台任务，候选记忆都经过同一条有界的
  校验、去重/冲突处理和提交路径。提取器本身不得直接改写 Session 或 Soul。
- Session 历史的读取、保留与恢复仍由 Session Storage 负责。Memory 的检索、
  Markdown 文件、索引、更新、遗忘和持久化属于 Memory 实现或产品。Core 只接收
  经选择的有界 Context 贡献；文件系统接口不进入 Core。

```text
已提交的完整 Session turn（原始记录保留）
    -> 应用触发器：显式命令 / Tool / 空闲期任务
    -> 有界候选生成：规则或模型，可能产生摘要与事实
    -> 准入：来源、身份、权限、大小、去重、冲突、确认
    -> Memory 提交：独立的 Markdown 文件与索引
    -> 后续 turn 的有界检索 -> Context Builder
```

### 数据与权限边界

- **自动摘要或提取**只读取已结束的完整 turn；中止或未知状态中的 Tool 副作用
  不能被概括成“已成功执行”。当前 JSONL 后端对掉电时执行中的 Tool 意图
  没有耐久保证，见 ADR 0016。显式用户设置或 `remember` Tool 可在活动 turn
  中提交，但 Tool 只有在 Memory 真正写入成功后才能返回“已记住”。
- 候选至少要能关联用户/租户范围、写入状态和来源：自动提取记录 Session 与
  turn 标识及提取器版本；显式写入记录用户命令或 Tool 请求标识。跨用户默认
  隔离；不能把甲的偏好用于乙的 Context。
- 模型生成的候选是**不可信数据**，不是新的系统指令。禁止从 Session 或普通
  Memory 自动改写 `soul.md`，也禁止隐式注册 Skill。Soul 的管理边界见 ADR 0023。
- “记住偏好”与“设备当前状态”不同：后者应以设备真实状态为准，不能因一次
  对话陈述永久覆盖。含敏感信息的候选可由产品拒绝、脱敏或要求用户确认。
- 事实冲突应以显式纠正、时间和来源规则处理，不以“最新模型输出”无条件
  覆盖旧记忆；遗忘请求必须传播到索引与缓存。Memory 文件的提交应由后端保证
  不留下半写入的 Markdown；具体原子性取决于所选文件系统。

### 执行、容量与失败

- 提取任务使用独立的消息窗口、输入/输出缓冲、超时与调用次数上限；不占用
  正在执行的 Core turn scratch。自动任务只能在产品允许的任务上下文中运行，
  不从 ISR 发起，也不默认复用一个正忙的 Model/Transport 实例。
- 摘要需标注覆盖范围，不能偷偷替代或删除原始 Session。多个摘要可以分层
  整合，但每次整合仍应保留可追溯的来源边界。
- 后台提取失败不回滚已完成的用户 turn；记录失败并由应用决定重试。显式
  Memory Tool 的写入失败必须向该 Tool 调用返回错误，不得告知用户“已记住”。
- 为减少 Flash 写放大，可先累计候选，再在空闲期有界批量提交；具体频率、
  文件布局和保留策略属于产品，不写死在通用库中。
- 去重与重试必须有稳定的来源标识和提交状态；仅靠“再跑一次 LLM 并比较文本”
  无法保证幂等。即使处理同一 turn，也可能产生不同措辞的候选。

### 当前接口缺口与分阶段落地

目前 `agent_session_storage_ops_t.recent()` 只能按 Session ID 读取最近 N 个完整
group，回调不提供稳定 turn ID 或前向游标。后续
[ADR 0032](0032-memory-domain-management.md) 已补整文 Memory 读取、替换与
遗忘契约，但没有来源索引与增量提取器。因此现有 API 可以做小窗口试验，
仍不足以可靠地增量扫描长历史并恢复提取进度。

1. 先用应用明确输入或 Tool 建立最小 Memory 写入、检索与删除闭环；保留原始
   Session，不修改 `agent_run()` 的成功语义。
2. 再基于真实产品需求定义来源 turn 的稳定标识、进度游标与重试语义。可由
   Session Storage 提供元数据/扫描能力，或由应用维护独立索引；不能假定现有
   `recent()` 已能覆盖完整历史。
3. 最后加入可选提取器和空闲期调度，并评估摘要质量、误记率、预算与 Flash
   写入量。是否需要公开 Memory ops，应在这条链路有测试后决定。

本文不规定 Markdown 的目录结构、front matter 格式、向量索引或特定模型
协议，也不新增公共 C API。

## 不采用的方案

### 自动压缩后删除或覆盖原始 Session

摘要有损，无法恢复对话、Tool 调用和副作用事实，也会把提取错误固化为唯一
历史；拒绝。

### 在 `agent_run()` 返回前强制同步提取并落盘

这会让交互延迟、网络依赖、能耗与 Flash 写入次数取决于可选 Memory 功能；
任一提取失败还会污染原本成功的 turn 状态；拒绝作为通用库默认行为。

### 让模型直接编辑 Markdown 或 Soul

绕过身份隔离、容量、冲突和确认策略，使普通对话有机会提升为受信任指令；
拒绝。模型只能提出候选或受控 Tool 请求。

## 验证要求

- 原始 Session 在成功提取、失败、重试、去重及 Memory 删除后保持不变；
- 同一来源重复处理不会产生重复条目；不同用户/Session 的候选不会串用；
- 修改或删除 Memory 后，后续 Context 检索不再返回旧值，Soul 和 Skill 不受影响；
- 后台提取不读取不完整 turn；显式 Tool 写入、模型幻觉、文件写入失败与
  断电重启均有可测试的处理结果；
- 内存峰值、模型调用次数、输出长度和持久化写入量均在产品预算内。
