# ADR 0027: 最小 Markdown Memory 文件布局

- 状态：提案
- 日期：2026-10-01
- 关联：[ADR 0010](0010-context-projection.md)、[ADR 0016](0016-session-history-storage.md)、[ADR 0023](0023-file-backed-memory-soul-skill.md)、[ADR 0024](0024-session-to-memory-extraction.md)

## 背景

产品希望用少量可检查的 Markdown 文件保存 Agent 身份、用户资料和长期记忆，
并保留每日笔记作为尚待整理的工作层。原先考虑过 `IDENTITY.md`、
`preferences.md` 和 `projects.md` 等独立文件，但对轻量嵌入式产品来说，
过早细分会增加加载、更新、权限和容量管理成本。

这里的磁盘文件目录不是 RAM 中的 `agent_workspace_t`；原始 Session 历史
也不是 Markdown Memory。需要明确每种文件由谁维护、何时进入 Context，
避免把每日笔记或用户资料误当成高权限系统指令。

## 决定

首版只约定四类**逻辑文件**，以单用户产品为示例：

```text
agent_data/
├── SOUL.md
├── USER.md
├── MEMORY.md
└── memory/
    └── YYYY-MM-DD.md
```

目录名称是应用侧的数据布局建议，**不是 Core 公共 API 或强制扫描规则**。
应用可以把文件放在不同分区，或从非文件介质提供等价内容；无文件系统的
产品不因本 ADR 被排除。文件缺失时的处理由产品显式配置，不能从文件名
存在与否推断能力已经启用。

| 文件 | 内容与更新者 | 本轮读取规则 |
|---|---|---|
| `SOUL.md` | 产品或授权管理员维护 Agent 身份、语气和稳定原则；少量名称/角色可合并在此，无须独立 `IDENTITY.md` | 作为受信任的产品配置加载稳定、有界快照；普通 Memory Tool 和自动提取器不可写 |
| `USER.md` | 当前用户的稳定资料、明确偏好和有效纠正；由用户或经授权的更新流程维护，无须独立 `preferences.md` | 按用户范围读取有界内容；不得把其中的叙述当作设备授权或系统策略 |
| `MEMORY.md` | 经筛选的长期事实、重要决定及少量摘要；由 Memory 提交流程维护，不放完整 Session、每日流水或无界项目记录 | 按预算选择完整内容或完整条目；超预算不静默截断成半条事实 |
| `memory/YYYY-MM-DD.md` | 当日观察、候选事实或阶段性摘要；应用或可选提取任务写入，允许尚未晋升为长期 Memory 的内容 | 默认不全文注入每轮 Context；按需有界检索，并可在后续任务中提炼到 `MEMORY.md` |

项目事实在确有价值时先进入每日笔记，经筛选后以简短条目进入
`MEMORY.md`；首版不预设 `projects.md` 或项目目录。如果一个文件规模已
超出设备预算，应在实际产品需求下另行裁决分片或索引，而不是先增加
一组无人使用的公共文件名。

## 作用域与权限

- 上述示例只适用于明确的单用户工作区。多用户设备必须将 `USER.md`、
  `MEMORY.md` 和每日笔记按用户隔离，并使用应用可信身份选择目录；
  不能从模型 arguments 或 Session 文本推断用户身份。`SOUL.md` 可保持
  产品/Agent 级，但其作用域也需由应用配置。
- `SOUL.md` 可描述产品人格，**不能代替** Tool Policy、设备权限或
  应用强制的安全约束。Session、每日笔记和模型生成的 Memory 候选均为
  不可信内容，不得自动提升为 Soul 或改写它。
- `USER.md` 中的事实必须可纠正；`MEMORY.md` 与每日笔记的写入须遵守
  ADR 0024 的来源、冲突、去重、确认及遗忘规则。成功写入应以实际提交
  为准，不能因为模型声称“记住了”就返回成功。
- 单个 Markdown 文件的存在不代表可供模型读取。文件路径、读写权限、
  容量、缓存与更新时机由应用或可选加载器掌握；Core 只消费有界的
  Context 贡献。更新应在 turn 边界形成一致快照，避免一次请求读到
  新旧内容混合。

## 与 Session、Skill 和 Context 的关系

原始 Session 仍由独立的 `agent_session_storage_t` 保存，可使用 JSONL、RAM
或其他后端；**每日笔记不是原始历史的替代品**。Session 的完整 turn 可供
检索或提取，派生出的摘要/事实经过准入后写入每日笔记或 `MEMORY.md`，
但不能因提取成功而删除原始 Session。

本轮 Context 的默认来源顺序仍遵守 ADR 0023：应用基础指令、Soul、经
选择的 Skill 和 Memory 贡献，Session 历史单独成为结构化消息。
`USER.md` 属于受用户范围约束的资料贡献，可在 Soul 之后、普通 Memory
之前投影；其文本不能覆盖产品级指令。每日笔记仅按需选择完整片段，
不能把一个目录的全部文件拼进 prompt。

Skill 的文件与显式注册机制不在这四类 **Memory 文件**中。产品若使用
Skill，仍由独立加载器管理，不能因为工作区里存在 Markdown 文件就
自动注册。普通对话“请总结”由当前模型回答；Session 到 Memory 的
提取是应用调度的独立有界任务，不要求内置 `summarize` Tool。

## 时间、容量与失败

- 日期文件名需要可靠的产品时间来源和明确时区。设备在 RTC 未校准、
  网络时间不可用或日期回退时，不应把新笔记错误写入 `1970-01-01.md`
  等伪日期；应用应延后写入或使用可恢复的临时队列，待日期确定后归档。
- 应用分别限制 Soul、User、长期 Memory、单日笔记和本轮投影大小。
  每日笔记可能长期累积，保留天数、归档、Flash 写入频率与磨损预算
  属于产品策略；`max_history_turns` 只限制 Session 的本轮投影。
- 必需的 Soul 加载失败时应按产品配置中止本轮；可选的 User/Memory
  内容失败不能被伪装成空内容而无人知晓。不得把过长文件读完后再
  静默截断，也不得把写入失败报告为已保存。
- 加载器应保证借用缓冲在 Core 使用期间有效；文件更新、删除和缓存
  失效须有可测试的边界。底层文件写入的原子性、同步和掉电保证取决
  于具体后端，不由四个文件名自动获得。

## 不采用的方案

- **一开始就引入 `IDENTITY.md`、`preferences.md`、`projects.md`**：与
  Soul、User、Memory 的职责重叠，增加小设备的配置与投影开销。
- **把每日笔记作为每轮必读的 Context**：笔记随日期累积，延迟和
  token 开销不可控，还可能让未审查的候选内容长期占据模型输入。
- **将 Markdown 文件当作 Session Storage**：丢失完整 turn 顺序、消息
  角色和 Tool 调用/结果配对，不满足 ADR 0016 的历史契约。

## 实施状态与验证

本文确定内容分类和信任边界，最初不新增公共 C API。后续
[ADR 0032](0032-memory-domain-management.md) 已实现独立 Memory ops 和可选
Markdown 后端，可按配置读取、替换与遗忘文档；不是自动加载/提取方案。
Skill/Context 组装链尚未完成，每日笔记不自动注入。

基础测试已覆盖用户 Store 隔离、Soul 拒写、缺失与超容量、发布前/后失败、
非法日期及原始 Session 字节保持不变。后端不缓存文本，下次读取获取新内容，
既有调用方快照仍有效。日期来源可信性、未来 Context 投影、Memory 提取与
真实掉电结果仍需应用策略和后续验证。
