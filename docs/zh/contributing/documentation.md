# 文档组织与维护

开发者手册按任务组织，维护资料记录设计过程。不要让用户先读几十篇 ADR 才能运行一个 Agent。

## 信息架构

| 类别 | 目录 | 写作目标 |
|---|---|---|
| 教程 | getting-started/ | 从环境到可运行结果，步骤完整 |
| 操作指南 | guides/ | 针对真实任务说明装配、失败与生命周期 |
| 接口参考 | api/ | 函数、字段、所有权、零值与错误 |
| 平台指南 | platforms/ | 构建依赖、SDK 限制、资源与验收 |
| 原理解释 | architecture.md、arch/ | 模块关系、数据流、内存与不变量 |
| 维护资料 | development/、adr/ | 实施事实、设计动机、候选与取舍 |

组织方式参考 [Diátaxis](https://diataxis.fr/) 的四类文档，
借鉴 [Zephyr 文档](https://docs.zephyrproject.org/latest/) 的平台接入路径与
[libcurl API](https://curl.se/libcurl/c/) 的专题参考组织，不复制其正文或架构。

## 当前事实与历史材料

主手册按当前源码组织，不按计划阶段描述 API。
不承诺未来能力已经可用，也不以“草案”代替清晰的现有契约。
ADR 保留历史状态；存在候选 API 时显式写明不是调用参考。
开发日志保留记录日期，不将一次 Host 通过升级为全平台支持保证。

当前优先级：公共头与实现/测试 → 使用手册 → 历史记录中的目标方案。
发现矛盾应修正文档并补测试，而不是要求用户自行猜测。

## 链接与示例

- 站内使用相对 .md 链接，所有用户页面进入 sidebars。
- 仓库源码使用 GitHub 绝对链接，不使用开发者机器绝对路径。
- API 标识和 C 类型放进代码块/行内代码，避免 MDX 误解析。
- 示例明确是完整程序、可嵌入函数，还是伪代码；不使用不存在的 API。
- 快速开始在 Host 实际编译运行，平台片段不能冒充完整 BSP。
- 添加接口时同步更新指南、参考、构建开关及必要的架构说明。

本地验证与预览命令见[文档维护入口](https://github.com/Scintela/cAGENT/blob/main/docs/README.md)。
